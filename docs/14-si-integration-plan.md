# План: SI-інтеграція для подання (кінцевий)

Замінює для хакатону `docs/13-si-fill-plan.md` і `docs/12-corpus-plan.md` з гілки `data-ai/si-fill-bass`.
Ті плани лишаються як перелік роботи після хакатону (розділ 10).

## 1. Навіщо

Челендж просить «SI-powered, web-based dashboard that summarizes, ranks, and interprets» дослідження.
До цього плану продукт був зроблений з допомогою SI, але сам на SI не працював:

- сайт у двох місцях писав, що AI не задіяно; `pipeline/cards.py` не викликає модель;
- текст подання казав, що AI немає в жодному числі, яке бачить користувач;
- слово «interprets» нічим не було закрите: прогалини й знахідку рахує код, тлумачення не було.

## 2. Рішення

SI робить три речі, кожна лишає файл у репозиторії, і кожну перевіряє код.

| # | Що робить SI | Яке слово челенджу закриває | Як перевіряється |
|---|---|---|---|
| A | пише короткий **SI brief** для кожного готового сценарію з уже порахованих фактів | interprets, ranks (пояснення) | кожне число й назва дослідження в реченні мають збігатися з фактом, на який речення посилається; перевірка працює в тесті й у браузері |
| B | читає **нотатки оператора BASS** (вільний текст у As Run Test Matrix) і визначає `ignited`, `outcome`, `burnTimeS` | extract data for predictive modeling | значення приймається, лише якщо його дослівна цитата є в клітинці NASA |
| C | **показана чесно**: розділ на Methodology з числами, позначка SI біля значень, оновлені тексти подання | summarizes | числа розділу рахуються з даних, а не пишуться вручну |

Незмінне:

- сайт лишається статичним, моделі під час роботи сайту немає (правило 8 `AGENTS.md`);
- бал ранжування рахує відкритий код, SI його не виставляє (правило 6);
- SI не робить фізичних висновків: brief говорить про покриття даних, а не про горіння (розділ 8 `AGENTS.md`);
- немає джерела — немає значення (правила 1, 2, 5).

Ключа API в команди немає, тому тексти й прочитання пише агент Claude Code у сесії (модель записана у файлі
результату). Файл результату той самий, що дав би виклик API, і перезбірка його не змінює.

## 6. SI brief (A)

**Факти.** `buildBriefFacts(scenario, investigations, tests)` у `apps/web/src/domain/brief.ts` повертає плоский
словник `ключ → число | рядок | null`, зібраний лише з функцій, які вже рахують екран Scenario
(`rankInvestigations`, `collectGapFacts`, `testedConditions`). Приклади ключів: `near.count`, `near.total`,
`tested.o2Max`, `exploration.allTests`, `rank.1.name`, `rank.1.score`, `partial.realTests`.
Команда `npm run brief-facts` у `apps/web` пише факти п'яти сценаріїв у `brief-facts.json`: це вхід для моделі.

**Файл.** `apps/web/src/content/briefs.json`: модель, версія інструкції, дата і для кожного сценарію масив речень
`{ text, facts: [ключі] }`. Інструкція для моделі лежить поруч у `briefs.prompt.md`.
Файл належить сайту, а не контракту: brief залежить від ранжування, яке рахує сайт.

**Перевірка** (`verifyBrief`, чиста функція):

1. кожен ключ із `facts` існує у фактах сценарію;
2. кожне число в тексті дорівнює якомусь із названих фактів, округленому до тієї кількості знаків, з якою число записано;
3. кожна назва дослідження в тексті є серед названих фактів;
4. слова «no», «none», «zero», «never» допускаються лише в реченні, де хоча б один названий факт дорівнює нулю або `null`.

Тест `src/lib/briefs.test.ts` проганяє перевірку на справжніх даних, тому після зміни даних застарілий brief зупиняє CI.
Сайт запускає ту саму перевірку в браузері й не показує речення, яке її не пройшло.
Перевірка не оцінює, чи речення вдале: вона гарантує, що його числа й назви взяті з даних.

**Показ.** Картка під знахідкою на Scenario, лише коли середовище точно дорівнює готовому сценарію.
Підпис: хто написав, скільки чисел і назв перевірено. Розгортання «What was checked» показує факти кожного речення.
Для власних значень картки немає, є один рядок пояснення.

**Як оновити brief після зміни даних.** `npm run brief-facts`, переписати речення за `briefs.prompt.md`,
`npm test`. Якщо тест падає, він називає речення й число, яке не збіглося.

## 7. Нотатки оператора BASS (B)

**Джерело.** `PSI-26_Science Documents_As Run_Test Matrix.xlsx`, аркуш `as run matrix`, колонка
«Test Observations and Anomalies (ignited, spread, extinguished, burn time, color, etc.)». Текст є в усіх
121 рядку, що відповідають тестам таблиці BASS. Файл уже завантажений пайплайном і поєднаний з таблицею ключем `join`.

**Файл прочитань.** `pipeline/mappings/si/PSI-26_BASS-notes.json`: для кожного ключа рядка матриці значення
й цитата для кожного з трьох полів; поля немає, якщо в тексті відповіді немає. Правила читання —
`pipeline/mappings/si/README.md`. Головні:

- `ignited: false` лише коли займання пробували справним запальником; зламаний запальник нічого не каже про матеріал;
- `self-extinguished`: згасло саме або на малому, але ненульовому потоці; `flow-terminated`: згасло, коли вимкнули потік;
  `burned-out`: паливо скінчилось; `other`: погасив азот;
- час горіння лише той, що прямо записаний у нотатці; з двох міток часу не рахуємо.

**Рушій.** Ключ маппінгу `siNotes` вказує колонку й файл прочитань. Для кожного рядка код (`pipeline/normalize/si_notes.py`):

1. бере текст клітинки з поєднаного рядка;
2. приймає значення, лише якщо цитата є в цьому тексті символ у символ, `outcome` входить у перелік контракту,
   а час горіння є числом з одиницею, яке стоїть у цитаті;
3. відкидає обидва поля, якщо `ignited` і `outcome` суперечать одне одному;
4. пише поле, додає його в `inferred`, цитату в `notes`;
5. відкинуте пише в `data/review/si-notes-rejected.csv` з причиною.

Значення з таблиці NASA не перезаписується ніколи.

**Результат.** 205 значень: `ignited` у 113 тестах (106 так, 7 ні), `outcome` у 75 (32 self-extinguished,
22 flow-terminated, 12 burned-out, 7 not-ignited, 2 other), `burnTimeS` у 17. Відкинуто 0.
Змінились лише рядки BASS; картки досліджень і сценарії не змінились.

**Показ.** У таблиці Tests наслідок, прочитаний SI, має позначку `SI`; у розгорнутому джерелі рядка видно
нотатки з цитатами, чи зайнялось і час горіння. Експорт CSV і JSON уже містить `notes` та `inferred`.
На Methodology: скільки тестів мають наслідок і скільки з них узято з документа.

**Обмеження контракту.** У контракті 1.1.0 немає поля, яке каже «це значення прочитала модель». Тому сайт
впізнає такі рядки за початком речення в `notes` («Read by SI (»), рядок записаний у `apps/web/src/domain/config.ts`.
Це працює, але тримається на тексті. Пропозиція власнику контрактів (один абзац для чату команди):

> Пропоную контракт 1.2.0: необов'язкове поле `fills` у `TestRecord` — масив записів
> `{ field, method: "si-text", sourceFile, locator, quote, model }`, не більше одного на поле; `field` має бути
> в `inferred`, а саме поле не `null`. Пайплайн уже має всі ці значення в `pipeline/normalize/si_notes.py`
> і зараз складає їх у текст `notes`. З полем сайт покаже позначку SI й цитату біля кожного значення,
> а експорт отримає окремі колонки з цитатами. Чинні поля не змінюються, рядки без таких значень поля не мають.
